## 1. 沙箱（精简版 → 完整版）

### 1.1 v2.2 现状（GA 前简化版）

- **范围**：M5.1 沙箱（精简版）— 本地 Docker 沙箱
- **实现**：标准 Docker 容器
- **限制**：
  - 不做 gVisor / Firecracker 隔离
  - 不做网络命名空间隔离
  - 不做完整审计日志
  - 不做实时监控仪表盘

### 1.2 完整版规划（GA 后）

| 模块 | 简化版 | 完整版 | 说明 |
|------|:---:|:---:|------|
| **容器运行时** | Docker | gVisor / Firecracker | 强隔离 |
| **网络隔离** | 默认 | Network Namespace + 防火墙 | 防数据外泄 |
| **资源限制** | Docker limit | cgroups v2 + 细粒度配额 | 防止资源滥用 |
| **审计日志** | SQLite | 结构化日志 + ELK | 可搜索 + 可分析 |
| **实时监控** | 无 | 仪表盘 + 告警 | 异常即通知 |
| **安全策略** | 无 | 完整安全策略 | 白名单 / 黑名单 |
| **多租户** | 单租户 | 完整多租户隔离 | 企业级 |

### 1.3 启动条件

- 收入 > ¥10 万/月（雇得起运维）
- 或 3+ 客户明确需要企业级安全
- 或有合规要求（金融 / 医疗 / 政府）

### 1.4 估计投入

- 设计：2 周
- gVisor / Firecracker 集成：3 周
- 审计 + 监控：2 周
- 测试 + 上线：2 周
- **总计：2 个月**

## 3. LoRA 微调（行业专属模型）

### 3.1 v2.2 现状

- **决策**（v2.0 关键）：**纯 prompt + few-shot**，不碰 LoRA
- **资源约束**：4 核 8G 宝塔跑不动 LoRA 训练
- **质量**：prompt 工程已达 6/10 准确率，剩余 4 分靠数据量堆

### 3.2 完整版规划

- **支持模型**：7B / 13B（Qwen / GLM / Llama）
- **训练方式**：LoRA（参数高效微调）
- **私有数据集**：用户上传 + 培训数据自动导出
- **训练监控**：loss 曲线 + 评估分数
- **模型评估**：v1 vs v2 对比
- **模型部署**：训练后自动部署到 LLM Gateway

### 3.3 启动条件

- 收入 > ¥5 万/月（覆盖 GPU 成本）
- 有 GPU 服务器（至少 24G 显存，建议 A100 / 4090）
- 用户明确需要行业专属模型

### 3.4 估计投入

- 训练框架集成：2 周
- 数据集管理：1 周
- 训练监控：1 周
- 评估 + 部署：2 周
- **总计：1.5 个月**

### 3.5 与"纯 prompt"的关系

- **不是替代**——是补充
- 行业模型（LoRA）+ 通用模型（prompt）= **混合架构**
- 用户可选：用 LoRA 提质量 / 用 prompt 省成本

## 7. WordPress 式生态（M6 2027-05+）🟣

> **这是 v2.3 远期愿景的完整规划**——把 AgentWork 升级为"AI 智能体领域的 WordPress"。

### 7.1 核心洞察

> WordPress 之所以能统治互联网 20+ 年，不是因为 WordPress 本身多强，
> 而是因为它打造了"**核心 + 主题 + 插件 + 应用市场 + 在线服务**"的可扩展生态。
> AgentWork 的终极目标就是成为 **"AI 智能体领域的 WordPress"**。

### 7.2 WordPress vs AgentWork 映射

| WordPress 概念 | AgentWork 对应 | 远期目标 |
|----------------|----------------|----------|
| **核心（Core）** | AgentWork 内核 | 员工定义 + 培训引擎 + 模板引擎 |
| **主题（Theme）** | 行业主题 | 5 核心 + 5 候补 + N 第三方主题 |
| **插件（Plugin）** | 员工能力插件 | 邮件 / CRM / 支付 / OCR / 知识库 |
| **应用市场** | 模板 + 插件市场 | 30+ 模板 + 100+ 插件 |
| **在线服务** | 云集云服务 | LLM Gateway / 同步 / 备份 / 监控 |
| **用户生态** | 创作者 + 开发者 | 收入分成 + 培训认证 + 合作伙伴 |

### 7.3 远期 M6 阶段任务（4-6 个月，2027-05~10）

### 7.4 6 层生态体系

#### 第 1 层：核心（Core）— AgentWork 内核
- 员工定义引擎（YAML + 验证）
- 培训引擎（RAG + 规则 + 话术 + 评估）
- 任务调度引擎（DAG + 重试 + 状态机）
- 插件加载器（动态加载 + 沙箱隔离）
- 主题渲染器（UI 主题切换）
- API 网关（内部 + 外部）

#### 第 2 层：产品周边（Product Periphery）— 对外能力
- **REST API**：
  ```
  POST /api/v1/employees/{id}/chat
  POST /api/v1/templates/{id}/install
  GET  /api/v1/employees/{id}/status
  ```
- **Webhook**：事件订阅（on_message_received / on_task_completed / on_employee_error）
- **CLI**：`yunji employee chat fashion_stylist --message "推荐搭配"`
- **SDK**（Python / Node.js / Go）：让开发者集成到自己的应用
- **嵌入式**：把 AI 员工嵌入 Web / 桌面 / 移动（iframe / SDK / 小程序）

#### 第 3 层：开发者生态（Developer Ecosystem）— 插件 + 集成

  - CRM 插件（Salesforce / 飞书 / 销售易 / 钉钉）
  - 支付插件（支付宝 / 微信 / Stripe / PayPal）
  - 数据分析插件（SQL / Pandas / 图表）
  - OCR 插件（百度 / 腾讯 / 阿里 OCR）
  - 知识库插件（Notion / 飞书文档 / 语雀）

## 10. 决策记录

### ADR-008：未来规划单独建文档

**决定**：把 IMPROVEMENT-PLAN.md 中"暂缓/砍掉/远期"内容迁移到 FUTURE-PLANS.md。

**理由**：
- IMPROVEMENT-PLAN.md 专注于"现在做什么"
- FUTURE-PLANS.md 专注于"未来做什么"
- 避免 IMPROVEMENT-PLAN.md 越来越臃肿
- 保留"未来想做"的想法
- 文档分工清晰

**影响**：
- IMPROVEMENT-PLAN.md 头部加"配套 FUTURE-PLANS.md"链接
- FUTURE-PLANS.md 是"参考预留"——不进 GA 1.0 时间线
- 等资源/收入/需求触发后再启动对应章节

### ADR-009：沙箱"简化版先做，完整版留未来"

**决定**：M5.1 沙箱只做本地 Docker 沙箱（简化版），完整版（gVisor + 审计 + 监控）放 FUTURE-PLANS.md。

**理由**：
- 4 核 8G 宝塔跑不动 gVisor / Firecracker
- 标准 Docker 沙箱对早期用户够用
- 完整沙箱需要专门的运维投入（雇得起人再做）

### ADR-010：LoRA 微调"暂不做，纯 prompt 够用"

**决定**：培训系统用纯 prompt + few-shot，不碰 LoRA 微调。

**理由**：
- LoRA 训练需要 GPU，宝塔 4 核 8G 跑不动
- prompt 工程 6/10 准确率已够用，剩余 4 分靠数据量堆
- LoRA 是"质量锦上添花"，不是"功能必须"

### ADR-011：私有化部署"按需议价，不做完整版"

**决定**：完整企业私有化部署放 FUTURE-PLANS.md，当前只做 SaaS。

**理由**：
- 私有化需要专业运维团队
- 4 核 8G 单实例撑不起多租户
- 等有客户明确要求再启动

### ADR-012：跨平台"桌面优先，移动端延后"

**决定**：先做 Tauri 桌面端（Windows / macOS / Linux），iOS / Android 留未来。

**理由**：
- 桌面端是 B 端主力场景（开发 / 客服 / 财务都在 PC 前）
- 移动端需要专门团队（Swift / Kotlin）
- 资源不够，先做桌面

1. 触发条件已满足
2. 季度检查决定启动
3. 完成 4 周评估期
4. 立项完成（v_n+1）

**从 IMPROVEMENT-PLAN.md 迁移到 FUTURE-PLANS.md 的触发条件**：
1. 资源不够（时间 / 人 / 服务器）
2. 优先级被其他更紧急的工作挤压
3. 客户需求变化
4. 决策调整

### 14.3 同步检查

每次更新 IMPROVEMENT-PLAN.md 时，同步检查 FUTURE-PLANS.md：
- 是否需要补充新的未来规划？
- 已启动的规划是否要标注"已迁移到 IMPROVEMENT-PLAN.md"？
- 触发条件是否需要更新？
