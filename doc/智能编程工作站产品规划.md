# 云集智能编程工作站 — 产品规划

> 版本：v1.0 | 日期：2026-05-25
> 定位：**AI 原生的工作空间，不是 AI 工具**
> 战略：**产品先行，鸡生蛋**

---

## 一、产品定位

### 1.1 一句话定义

**云集智能编程工作站** — 一个 AI 原生的编程工作空间，AI 居民在其中主动感知、持续进化、协作创造。

### 1.2 与竞品的根本差异

所有竞品都是 **"AI 工具"** — 人发指令，AI 执行，用完即走。

我们是 **"AI 工作站"** — AI 是工作站的居民，始终在场，主动感知，持续进化。

| 维度 | AI 工具（竞品） | AI 工作站（我们） |
|------|---------------|-----------------|
| AI 角色 | 被调用的工具 | 工作站的居民 |
| 交互方式 | 人指挥 AI 干活 | 人和 AI 共存于工作站 |
| 知识归属 | 会话级，关掉就丢 | 工作站级，永久积累 |
| 成长性 | 不成长 | 越用越懂你 |
| 社会性 | 单个 AI | 多 AI 协作 |
| 感知能力 | 被动等待指令 | 主动感知环境变化 |

### 1.3 名字的意义

**工作站** = 空间 + 工具 + 环境

- 空间 — AI 居民生活和工作的地方
- 工具 — 编程、调试、部署的完整工具链
- 环境 — 知识、记忆、技能的持久化生态

未来自然演化路径：
```
云集智能编程工作站（Phase 1，聚焦编程）
  → 云集智能工作站（Phase 2，扩展全域）
    → 云集（Phase 3，品牌即品类）
```

## 二、六大革命性特性

### 2.1 特性总览

| # | 特性 | 一句话 | 竞品现状 |

| 1 | 主动感知引擎 | AI 主动发现问题，不需要人问 | ❌ 全部被动 |

### 2.2 特性一：主动感知引擎（Responsive Engine）

**核心理念**：AI 不应该等你问，它应该主动告诉你。

| 感知能力 | 说明 | 触发条件 |
|---------|------|---------|
| 文件变更感知 | 监控项目文件变化，理解变更意图 | 文件保存时 |
| 代码质量巡逻 | 扫描代码异味、安全漏洞、性能问题 | 后台定时 / 文件变更时 |
| 依赖风险预警 | 检测过时依赖、已知漏洞 | 项目打开时 / 定时 |
| 上下文主动推送 | 根据当前工作推送相关文档/代码 | 编辑文件时 |
| 进度追踪提醒 | 记住未完成任务，下次打开主动提醒 | 工作站启动时 |
| 测试失败预警 | 测试失败时主动通知并建议修复 | 测试运行后 |

**交互示例**：

```
🤖 工作站通知：
  我注意到 utils.py 中的 parse_json() 在3处被调用，
  但2处没有异常处理，可能导致线上崩溃。
  [查看详情] [自动修复] [忽略]

🤖 工作站通知：
  你上次在这个项目中完成了"用户注册API"，
  还剩"登录API"和"邮箱验证"未完成。要继续吗？
  [继续开发] [查看计划] [稍后提醒]

🤖 工作站通知：
  requirements.txt 中的 flask 版本 2.3.0 有已知安全漏洞，
  建议升级到 3.0.0。
  [升级] [查看详情] [暂不处理]
```

**技术实现**：

```python
class ResponsiveEngine:
    WATCHERS = {
        "file_change": FileChangeWatcher,
        "code_quality": CodeQualityPatrol,
        "dependency": DependencyRiskScanner,
        "progress": ProgressTracker,
    }

    async def start(self, workspace_path: str):
        for name, watcher_cls in self.WATCHERS.items():
            watcher = watcher_cls(workspace_path)
            async for notification in watcher.watch():
                await self._notify_user(notification)
```

### 2.3 特性二：自进化知识系统（Self-Evolving Knowledge）

**核心理念**：每一次交互都是知识金矿，不能浪费。

#### 知识四层架构

| 层级 | 类型 | 价值 | 示例 | 演化规则 |
|------|------|------|------|---------|
| L1 | 纠正（Corrections） | 🔴 最高 | "不要用 var，用 const" | 永不再犯 |
| L2 | 模式（Patterns） | 🟡 高 | 用户连续3次手动测试→提交→部署 | 自动提炼为 Skill |
| L3 | 事实（Facts） | 🟢 中 | "这个项目用 PostgreSQL" | 持久化存储 |
| L4 | 偏好（Preferences） | ⚪ 低 | "我喜欢 Tab 缩进" | 自动应用 |

#### 强度演化模型

```
新知识创建 → strength: weak, confirmed: 0
  ↓ 应用一次未被纠正
strength: weak, confirmed: 1
  ↓ 再次应用未被纠正
strength: medium, confirmed: 2
  ↓ 反复验证
strength: strong, confirmed: 4+
  ↓ 用户明确确认（"对，就是这样"）
strength: strong（立即跳升）

当项目级知识达到 strong 且不含项目特定引用时
  → 建议提升为全局知识（用户确认后才提升）
```

**为什么不自动提升？** 因为虚假提升的成本（污染全局）远超遗漏提升的成本（再教一次）。

#### 知识存储

```
.yunji/
├── knowledge/
│   ├── corrections.md    # L1 纠正记录
│   ├── patterns.md       # L2 工作流模式
│   ├── facts.md          # L3 项目事实
│   ├── preferences.md    # L4 用户偏好
│   └── strength.json     # 知识强度追踪
```

### 2.4 特性三：多智能体协作引擎（Multi-Agent Engine）

**核心理念**：多智能体不等于更智能，等于必须先治理。

#### 两种模式

| 模式 | 名称 | 说明 | 适用场景 |
|------|------|------|---------|
| 独行模式 | 一个 AI 独立完成 | 单 Agent 深度编码 | 修 Bug、写函数、代码审查 |
| 团队模式 | 多 AI 角色协作 | 多 Agent 并行 + 边界治理 | 项目开发、架构设计、全栈实现 |

#### 团队模式角色边界治理

借鉴 Harness Craft 的核心洞察，每个角色有明确的读写范围：

| 角色 | 写入范围 | 职责 | 分离原因 |
|------|---------|------|---------|
| 主管 | 集成和仲裁 | 任务契约、冲突解决、最终验证 | 必须保持单点真相 |
| 架构师 | 只读 | 设计简报、风险热点、文件影响图 | 设计必须先于变更 |
| 开发工程师 | 生产代码 | 最小安全实现 | 将实现与其他问题隔离 |
| 测试工程师 | 测试代码 | 测试覆盖率、回归保护 | 使验证成为独立责任 |
| 审查员 | 只读 | 审查集成结果 | 避免对半成品无焦点反馈 |

#### 关键规则

1. **一个会话一个功能** — 范围扩展是最高杠杆的控制点
2. **角色边界不可逾越** — 开发工程师不能写测试代码
3. **交叉审查** — 开发完成后，测试工程师自动审查
4. **主管仲裁** — 角色间分歧由主管决定
5. **知识共享** — 一个角色学到的经验，所有角色共享

### 2.5 特性四：工程化持久化（Durable Engineering）

**核心理念**：上下文活在项目里，不是聊天里。

```
旧范式：上下文活在聊天记录中
  关掉对话 → 丢失一切 → 下次从零开始

新范式：上下文活在项目文件中
  .yunji/
  ├── state.json          # 机器可读的项目状态（单点真相）
  ├── memory.md           # 工作记忆（进行中的上下文）
  ├── plan.md             # 当前计划和进度
  ├── checklist.md        # 执行账本和验证状态
  ├── knowledge/          # 持久化知识库
  │   ├── corrections.md
  │   ├── patterns.md
  │   ├── facts.md
  │   └── preferences.md
  ├── skills/             # 自动生成的技能
  └── agents/             # Agent 角色配置
```

**为什么分成6个文件而不是1个？**

| 文件 | 为什么不能合并 |
|------|--------------|
| state.json | 需要被脚本读取，不能是自然语言 |
| memory.md | 与项目事实混合后变成无结构日记 |
| plan.md | 未来行动不等于过去执行 |
| checklist.md | 真实进度不应该被改写成设计散文 |
| knowledge/ | 知识是跨会话的，不属于单次会话 |
| skills/ | 技能是可复用的，不属于单个项目 |

**这意味着**：即使换了电脑、换了模型、关掉工作站再打开，项目知识依然完整。

### 2.6 特性五：GUI 原生工作站

**核心理念**：可视化操作，不是 CLI。

| GUI 能力 | 说明 | CLI 做不到 |
|---------|------|----------|
| DiffView | 红绿对比查看代码变更 | CLI 只能看文本 diff |
| 任务看板 | 可视化任务分配和进度 | CLI 只能看列表 |
| Agent 状态面板 | 实时看谁在做什么 | CLI 只能看日志 |
| 知识面板 | 查看 AI 学到了什么 | CLI 无法可视化 |
| 项目仪表盘 | 代码质量、进度、风险一览 | CLI 无法总览 |
| 代码变更回溯 | 点击步骤查看对应变更 | CLI 无法关联 |
| 审批节点 | 可视化审批流程 | CLI 只能输入 y/n |

### 2.7 特性六：本地模型支持

**核心理念**：离线也能用，数据不出本机。

| 能力 | 说明 |
|------|------|
| Ollama 代理 | 本地模型代理服务器，统一接口 |
| 智能模型路由 | 简单任务用本地模型，复杂任务用云端 |
| 隐私保护 | 敏感代码只走本地模型 |
| 离线可用 | 无网络时仍可编码 |
| 模型推荐 | 根据硬件自动推荐合适的本地模型 |

## 三、工作模式设计

### 3.1 独行模式（Single Agent）

**"一个 AI 独立完成任务"**

#### 核心流程

```
用户输入需求
  ↓
Plan 阶段：AI 生成开发计划，用户逐条确认
  ↓
Execute 阶段：AI 按步骤执行，每步可审查
  ↓
Review 阶段：DiffView 查看变更，可回退
  ↓
Learn 阶段：自动提炼知识，积累经验
```

#### Plan 模块

| 功能 | 说明 |
|------|------|
| 需求对话 | 开发前与 AI 讨论需求 |
| 方案生成 | AI 自动生成多个技术方案 |
| 任务拆解 | 将需求拆解为具体步骤（To-Do List） |
| 逐条审批 | 每个方案可独立采纳或拒绝 |

#### Tool 调度

| 工具 | 说明 | 后端 API |
|------|------|---------|
| read_file | 读取文件 | /api/system/file-tree |
| write_file | 写入文件 | /api/system/terminal/run |
| edit_file | 编辑指定行 | 新增 |
| search_code | 搜索代码 | 新增 |
| run_command | 执行命令 | /api/system/terminal/run |
| git_status | Git 状态 | /api/system/git/status |
| git_commit | Git 提交 | /api/system/git/commit |
| git_log | Git 历史 | /api/system/git/log |
| list_dir | 列出目录 | /api/system/file-tree |
| web_search | 网络搜索 | 新增 |

#### DiffView

| 功能 | 说明 |
|------|------|
| 变更视图 | 展示 AI 修改的文件、行号、增删内容 |
| 步骤关联 | 每个步骤可点击查看对应变更 |
| 单文件 Diff | 左右对比 |
| 变更回退 | 一键回退不满意的变更 |
| Session 回溯 | 基于最近 N 个 session 回溯 |
| 变更摘要 | AI 自动总结变更内容 |

### 3.2 团队模式（Multi-Agent）

**"多 AI 角色协作完成复杂项目"**

#### 核心流程

```
用户输入需求
  ↓
主管 Agent 分析需求，生成 Plan
  ↓
用户确认 Plan → 主管分配任务给各角色
  ↓
各角色并行工作（边界治理，互不冲突）
  ↓
关键节点人工审批
  ↓
交叉审查 + 主管仲裁
  ↓
交付 + 知识沉淀
```

#### 角色系统

| 角色 | 职责 | 输出物 |
|------|------|--------|
| 🎯 主管 | 统筹协调、冲突仲裁、最终验证 | 任务分配、审批决策 |
| 🏗️ 架构师 | 架构设计、风险评估 | 设计文档、文件影响图 |
| 💻 开发工程师 | 代码实现 | 生产代码 |
| 🧪 测试工程师 | 测试验证 | 测试代码、测试报告 |
| 📝 文档工程师 | 文档编写 | API文档、部署文档 |

#### 任务看板

```

│ 前端     │ 后端     │ 后端     │ 后端     │
```

## 十、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| Agent 执行不可控 | AI 可能执行危险操作 | 工具白名单 + 审批 + 沙盒 |
| 上下文窗口不足 | 复杂项目超出模型上下文 | 上下文压缩 + .yunji/ 持久化 |
| 多 Agent 冲突 | 多个 Agent 同时修改同一文件 | 角色边界治理 + 文件锁 |
| 感知通知过多 | 用户被通知淹没 | 严重度分级 + 智能过滤 + 免打扰 |
| 知识污染 | 错误知识被提升为全局 | 强度演化 + 人工确认提升 |
| Token 成本高 | 多 Agent + 感知消耗大量 Token | 智能模型路由 + 本地模型 + 缓存 |

## 十二、远程编码（手机→电脑）

### 12.1 核心理念

**电脑做后端，手机做前端。** 手机变成电脑的远程控制器，所有重活在电脑上跑，手机只负责展示和交互。

```
┌─────────────────────┐      WiFi/局域网       ┌──────────────────┐
│   📱 手机（前端）     │ ◄──────────────────► │  💻 电脑（后端）   │
│                     │    HTTP API + SSE      │                  │
│  AI 对话界面        │                        │  FastAPI         │
│  DiffView 查看代码  │                        │  文件系统         │
│  任务看板           │                        │  终端执行         │
│  感知通知           │                        │  Git 操作         │
│  审批节点           │                        │  Ollama 模型      │
└─────────────────────┘                        └──────────────────┘
```

### 12.2 杀手级场景

| 场景 | 描述 |
|------|------|
| 躺床上写代码 | 📱 跟 AI 说"写个注册接口" → 💻 执行 → 📱 DiffView 审查 → 采纳 |
| 通勤审查代码 | 📱 收到感知通知"安全漏洞" → 点击升级 → 💻 自动执行 |
| 开会远程调试 | 📱 发命令"查看日志" → 💻 tail -f → 📱 实时看到输出 |
| 外出监控项目 | 📱 收到"测试失败" → 让 AI 修复 → 💻 执行 → 📱 审查结果 |

### 12.3 技术实现

Web 化架构天然支持，几乎零额外开发：

```
桌面模式：pywebview 加载 http://127.0.0.1:18080
远程模式：手机浏览器打开 http://电脑IP:18080

需要做的：
  1. FastAPI 监听 0.0.0.0（而非 127.0.0.1）
  2. Token 配对认证
  3. 手机端 UI 响应式适配（已实现）
```

### 12.4 安全措施

| 措施 | 说明 |
|------|------|
| Token 配对 | 手机连接时需输入配对码（电脑端显示） |
| 局域网优先 | 默认只监听局域网，不暴露公网 |
| HTTPS | 远程访问时强制加密 |
| 操作确认 | 危险操作（rm/git push）需二次确认 |
| 会话管理 | 手机断开自动锁定 |
| IP 白名单 | 可配置允许连接的 IP 范围 |
