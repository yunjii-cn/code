# 文档治理规范

> 目标：让文档先于站点和产品计划稳定下来，避免全局文档、产品文档、历史对话混在一起。

## 1. 文档分层

### 1.1 根级 `doc/`

只放全局性内容：

- 云集品牌、公司级定位、产品线矩阵
- 跨产品商业模式、价格策略、升级路径
- 全局架构原则、身份体系、SSO 策略
- `work.yunjii.cn` / `aw.yunjii.cn` 站点计划
- 跨产品宣发和品牌素材

不要放：

- 某个产品的打包说明
- 某个产品的代码地图
- 某个产品的接口细节
- 原始长对话
- 已废弃路径的实现说明

### 1.2 产品目录文档

产品专属文档必须放在产品目录内：

| 目录 | 文档范围 |
|---|---|
| `1.PC/doc/` | PyQt6、本地桌面、离线、Ollama、便携环境、EXE、进程控制 |
| `2.WEB/doc/` | Web 化、多端、PWA、Capacitor、轻量 Pro 版体验 |
| `3.dev/doc/` | 云集团队版、Platformkit、团队协作、Business 档现行规划 |
| `4.AgentWork/docs/` | AgentWork、Tauri/Rust、AI 员工、AI 团队、行业模板、自进化 |

### 1.3 备份与低频历史材料

`BAK/` 用于保存无维护价值、低频查阅或只作证据留存的历史材料。根级 `doc/` 不长期保留 `archive/`，避免搜索和阅读成本持续上升。

各产品内只保留仍需要维护的现行或待复核文档；旧路径参考、旧规范、原始长对话和大型旧计划优先迁到 `BAK/`。

备份材料可以作为证据，但不能作为当前执行标准。任何引用都要回到以下文件校验：

- 根 [../AGENTS.md](../AGENTS.md)
- 根 [README.md](../README.md)
- [产品线矩阵.md](产品线矩阵.md)
- 对应产品 README / AGENTS

## 2. 命名规则

新文档优先使用清晰中文名：

- `产品线矩阵.md`
- `双站点开发计划.md`
- `文档治理规范.md`
- `身份与SSO策略.md`
- `站点视觉规范.md`

技术实现文档可使用英文模块名：

- `TimeFlow-设计.md`
- `OIDC-接入方案.md`
- `Platformkit-模块索引.md`

避免：

- 含糊命名：`新文档.md`、`整理.md`、`最终版.md`
- 聊天导出名作为正式文档
- 文件名只写日期不写主题

## 3. 文档状态

每份长期维护文档建议在开头标注：

```md
> 状态：现行 / 需复核 / 历史参考 / 草案
> 范围：全局 / 1.PC / 2.WEB / 3.dev / 4.AgentWork / 站点
> 最近更新：YYYY-MM-DD
```

状态含义：

| 状态 | 含义 |
|---|---|
| 现行 | 当前可作为执行依据 |
| 需复核 | 内容有价值，但可能存在旧路径、旧价格、旧技术栈 |
| 草案 | 方向讨论中，不能直接执行 |
| 历史参考 | 仅保存上下文，不作为规范 |

## 4. 迁移规则

移动文档时遵循：

1. 先判断文档归属：全局、产品、站点、归档。
2. 明显旧路径但仍有参考价值的文档，优先移动到 `BAK/`，必要时在当前索引保留归档链接。
3. 原始对话导出放入 `BAK/` 下的低频归档目录，后续只抽取结论进入正式文档。
4. 不直接删除大型历史文档，除非确认已有正式文档完整替代。
5. 更新 `doc/README.md` 和对应产品 `doc/README.md`。

## 5. 双站点文档边界

`work.yunjii.cn` 相关文档归根级 `doc/`，因为它是产品矩阵门户和统一身份入口。

`aw.yunjii.cn` 的市场定位、转化文案和站点计划也先归根级 `doc/`，但 AgentWork 产品能力细节仍归 `4.AgentWork/docs/`。

当两个站点独立成仓后，再复制或迁移站点专属文档到各自仓库。
